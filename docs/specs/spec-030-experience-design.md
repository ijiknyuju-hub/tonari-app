## ポジショニング（v2新設 — 全判断の最上位）

**一言定義**: となりごはんは、レシピを検索するアプリではなく、「作れる料理」を資産として育てる料理帳アプリ。

**戦略**: クラシル・クックパッド等の土俵（レシピ在庫×検索、KPI=閲覧数と広告）には乗らない。検索アプリの体験は消費（毎回ゼロから探す）、うちの体験は蓄積（使うほど資産が貯まる）。この非対称が戦略の核。狙う層は「記録は続かないが成長はしたい層」— れぴった型のこだわり記録層と巨人の検索層の間の空白。

**強み**: (1) 同梱データ資産 — 紹介文・特徴量・近さスコア・オーナー添削済み品質。AIで製造コストが個人でも払える時代になったからこそ先に張れる。(2) 育つスイッチングコスト — 料理帳・記録・マイレシピのピンは移行できない資産。人質型ではなく所有型（ユーザーのものだから離れたくない）。(3) ポジショニングの空白（上記）。

**弱み（正直に）**: ネットワーク効果はない。勝負は体験品質一本。オーナー判定の厳しさが堀を掘る作業そのもの。

**導線ループ**: 短尺動画（訴求軸=マンネリ「また同じ献立」）→ DL → オンボーディングの種まき（Day-1価値）→ 推測通知が記録を定着 → 月次サマリーカードがSNSに戻って再拡散。友人の動画編集/SNS運営分業はこのループの入口と出口に刺さる。「白地図が塗られていく」「十八番が決まる」は短尺で見せられる絵。

## 二本柱（全機能判断の基準）

レパートリー拡大の **コスト削減** × **モチベーション増加**。機能・画面・演出はどちらに効くかを明示できなければ入れない。

## アプリの本分

レシピ提供・調理のコツは主役にしない。「レパートリーを広げる」だけが主役。
例外: AI生成の詳しめレシピは全皿に同梱する（調べるのも面倒な人がここで完結するため）。AIレシピは「それなり」でよい（オーナー確定 2026-07-04: 最近のAI性能なら実用水準。むしろ無いと外部でレシピを探す手間が増えて続かない）。カード内の序列はYouTube埋込=主、AIレシピ=「下書き」ラベル付きの従。
最終目標（覚書）: レシピアプリ等との公式API連携によるレシピ取り込み。

## データ基盤: 近さスコア（v2新設 — 全体の背骨。ADR-009）

**転換**: 「ベース→となり」の手書きエッジ正本を廃し、**料理を特徴量で定義し、関係はスコアから導出する**構造にする。

- 特徴量: 食材・調味料・調理法（炒める/煮る/揚げる…）・工程数・難易度・ジャンル
- 近さ = 重み付き一致度（**無向**）。調味料の重みを高く — 味の近さと「買い足し1本で解放」の両方をこの軸が駆動する
- 推薦は最大値ではなく**バンド**から出す（「十分近いが同じではない」帯）。近すぎ=退屈、遠すぎ=なんで？の両失敗を防ぐ
- これにより: 一方向問題（星型1ホップ）は構造的に消滅 / 全料理が有機的に接続 / ユーザー追加料理も登録した瞬間にグラフへ自動参加（孤児ノードが生まれない）/ ホーム・探す・地図が全部スコア1本にぶら下がる
- **前提条件（実装前必須）**: 食材マスタ正規化（76生文字列→id+表示名）+ 料理名の**別名テーブル**（ガパオ/ガパオライス/鶏バジル炒めご飯）。スコアとキャプチャ照合の両方がこれに依存
- **人間レビューの範囲**: 事前レビュー対象は同梱分のみ — 実際に浮上する各皿上位5件≒600ペア前後の隣接妥当性（変な料理の排除）+ 紹介文添削。既存のNotionレビューフローをそのまま使う。実行時生成分（キャプチャ由来）はレビュー不能 → 下書きラベル+品質の実体は動画側で封じ込め
- **重み設計は未決**（未決リスト参照）。実データで調整

## カタログ編成（v2新設）

**原則: カタログは幹線道路だけ舗装する。** ロングテールは外部キャプチャで各ユーザーが自分で輸入する。

- 規模: **v1で主菜150〜200皿**。土台層=日本の定番家庭料理60〜80（オンボーディングの種。「よく作る料理」が8割ヒットしないとDay-1が死ぬ）+ フロンティア層=各系統へのブリッジ皿60〜80
- ジャンル比の初期仮説: 和50% / 中華・韓国20% / 洋20% / エスニック10%。オンボーディングの選択データ（どの皿が種にされたか=需要の実測）で補正
- **ブリッジ皿の意図的編成**: 「新規食材ちょうど1つ、他は全部手持ち」の皿を系統の境界に置く（ガパオ=ひき肉と玉ねぎは普段通り、新規はナンプラーだけ、が典型）。日本食への偏りは矯正しない — 偏りはコスト削減側が正しく働いている証拠。エスニックへの出口は「ナンプラー1本で作れる料理が4品増える」という**解放の提示**で作る
- **副菜・汁物 = 「おとも」層**（2026-07-04 オーナー確定・主菜中心は維持）: 主菜と副菜を結ぶのは近さ（似ている）ではなく**相性**（合う）。副菜は探索地図に置かず、**主菜カードの「あと一品」枠**に2〜3品ぶら下がる。定番時短副菜20〜30品+汁物少々、**全部10分以内縛り**。記録・ランク・料理帳への収まりは主菜と同一機構
- 現有資産: 120皿・紹介文165候補（Notionレビュー中）。増分は30〜80皿+ブリッジ配置で、準ベース選定と同じ作業内で編成可能

## 画面ごとの体験定義

### ホーム — コスト削減
おすすめは少なく。シンプルで洗練。構成の正本はNotion「おすすめ画面仕様書」（ADR-005/spec-024に転記済み）: ヘッダー→挨拶→難易度タブ（かんたん/少し広げる/しっかり作る）→「この前作った『〇〇』から広げる」+他の起点にする→メインおすすめ1件→小カード3件。各カードに難易度ラベル必須、工程量は出さない。
**v2追記**: おすすめには**既作・十八番未満の料理も含める**（2026-07-04 オーナー確定）— 反復が昇格ランクの燃料になる。新規:既作の比率は未決。推薦の実体は近さスコアのバンド。難易度タブとスコアバンドの対応関係は未決。

### 探すタブ — コスト削減
料理名の部分一致検索+食材チップフィルタの2入口を1画面に。対象は**自分のレパートリー内のみ**（作った+ブックマーク+取り込んだ料理）。カタログ全体逆引きはしない — 「探さなくても出てくる」の本分を守る。新規発見はホーム提案+地図の2経路。

### 料理帳 — モチベ増加（達成感・所有感）

原理: **中身入りで配られる料理帳**。れぴった型の弱点（登録するまで価値ゼロ）の逆。同梱データがあるから「作った」1タップの瞬間に完成品ページが勝手に生まれる。ユーザーは一度も「書く」必要がない。編集は「できる」が「しなくても美しい」。
**Day-1条件（v2明記）**: 「中身入り」が効くのは2日目以降。初日はオンボーディングの種まき（もう作れる料理を選ぶ=v2.7チップ式16品の資産流用）が全体重を支える。**オンボーディングは「配る瞬間」であり最重要画面**。

1. **1タップ記録**が唯一の入力。入口は3つ、太い順に:
   - **推測通知（生命線）**: レシピ/動画閲覧+時間帯のヒューリスティクスで「作ってそう」を推測 → 翌朝「昨日、〇〇作った？」通知に[作った/作ってない]アクションボタン。アプリを開かず1タップ。規律: シグナルが強いときだけ・1日1通まで・[作ってない]も1タップで責める色を出さない・外した推測は摩擦シグナルとして黙って記録。**AI不使用**（ヒューリスティクスのみ）。計測は通知応答率を代理指標に
   - アプリ内: 詳細画面の大きな「作った」ボタン+ホームカード直押し
   - **写真撮影=自動記録**（撮影行為自体が証拠。加点行動が記録を兼ねる）。取り逃しは詳細画面から日付付き後追い登録
2. **自動昇格ランク**: 回数で 作った→定番→**十八番**（手動スタンプ廃止。同日重複は1回扱い）
3. **成長サマリ**: 先頭に差分1行。**停滞時切替（v2確定）**: 月0〜1品の月はフロー表示（今月+3品）からストック表示（十八番3品・累計28品）に自動切替 — 停滞可視化を防ぐ。語彙に**食卓の完成度**を含める（「副菜レパートリーが5品に。一汁一菜が組めるようになった」）。成長の軸は3本: 主菜の広がり×十八番の深さ×副菜の完成度
4. **月次サマリーカード自動生成**（1080×1080、テンプレ合成・AI不使用・**写真非依存デザイン**）— SNS共有資産。当月分は常に無料
5. **URL添付は全皿の普遍フィールド**（v2昇格）: 編集・差し替え・複数添付自由、1つを**マイレシピとしてピン留め**。「いろいろ試してこの人が一番」の確定=習熟の証として料理帳に刻まれる。品質は外部から、の原則がユーザーの選球眼で完成する。外部キャプチャはこのフィールドの入口の1つに過ぎない
6. **カードは全フィールド編集自由**（名前・写真・紹介文・レシピ・メモ・URL）。実装はDishOverride上書き層 — カタログ更新がユーザー編集を潰さない。dish_id不変契約

**写真の扱い（v2確定 — 役割分離）**: 写真を撮らない層（めんどくさい/きれいに撮れない）を前提に設計する。
- 「めんどくさい」→ **写真ゼロでもページが恒久的に完成品**。ランクバッジ・回数・日付・イラストで美しく閉じる。台紙を「写真待ちの空欄」に見せない。写真は要求されない加点
- 「きれいに撮れない」→ **額縁**: 自動トリミング+統一フィルタ+カード枠（チェキ風/SnapDish系が実例）。美しさは枠側が担保し、ハードルは「上手く撮る」から「撮るだけ」へ
- 撮る人には「配られた料理帳が自分の写真で埋まっていく」所有感演出（DishOverride表紙写真、保存はexpo-file-system+パス参照、AsyncStorage base64不可）

**v1から外す**: 表紙ピッカー / コレクション命名 / 手書き風フォント / 手動スタンプ → **買い切りProの目玉としてv1.5で復活**（収益モデル参照。無料=勝手に育つ、Pro=こだわれる、の価値分割）

### 外部キャプチャ（v2新設 — 「自作料理」機能の再定義）

ゼロから料理を発明する人はほぼいない。実際の欲望は「YouTubeで見たこれ、作りたい」。将来構想だった「YouTube URL→カード自動生成」を**v1機能に昇格**。公式API連携（最終目標）への第一歩。

- フロー: 共有シート→となりごはん→oEmbedでタイトル/サムネ取得→AIが料理名を正規化→**近さスコアでカタログ照合**→3分岐:
  1. 高スコア一致 → 既存カタログ皿に紐付け（動画は添付に）。同梱の完成品ページを入力ゼロで獲得
  2. 曖昧帯 → 確認1タップ（「これは『ガパオライス』のこと？」はい/別の料理）
  3. 不一致 → 新カードをAI生成（特徴量推定+下書きラベル付き紹介文+スコアで関係自動接続）
- 取り込み先は「作りたい」（ブックマーク）。最頻ケースは共有→確認の2タップ、タイプ入力ゼロ
- **v1はYouTubeが一級市民**（oEmbed公式・Data API無料枠で足りる）。Insta/TikTokは「URL保存+料理名1フィールド」の格下対応
- **実装前実験（必須）**: 実在の料理動画URL30本でタイトル+概要欄→料理名抽出→カタログ照合をオフライン検証。目標: 上位1候補で8割、確認候補3提示で95%
- **binding**: 実行時の紹介文生成プロンプトにも紹介文ルールを**逐語で**埋める（165件全滅の教訓）

### 地図 — モチベ増加（v2方針差し替え: 白地図の塗り絵）

旧5案（路線図・星座・庭・街・放射グラフ）は全て不採用。敗因は様式から入ったこと+関係グラフをそのまま描こうとしたこと。v2方針:

- **地図 = 近さスコア空間の2次元投影**。軸に意味を持たせず「近い料理が近くに置かれる」だけの配置 — 固定2軸マトリクスの表現力問題を回避
- **地形は事前計算・固定出荷**: オフラインで一度だけ投影→オーナーが手調整（重なり解消・系統の島の形）→固定座標で出荷。理由: (1) 安定性 — レイアウトが動く地図は「自分の地図」としての馴染みを破壊 (2) アートディレクション可能性 — 絵としての美しさを運任せにしない
- **視覚性 = 白地図の塗り絵**: 全皿が線画アウトラインで常に描かれ（名前も形もはっきり見える — 霧ではない）、作った料理だけフルカラー+写真で塗られる。成長可視化は「隠す→現す」でなく「線画→彩色」
- **網羅性と扱いやすさ = ズームの役割分担**: デフォルトカメラは自分のレパートリー周辺、ピンチアウトで全世界図。遠景=系統の島と塗り具合、近景=皿の顔
- **探索の楽しみ = 2機構**（どちらもスコアから導出、専用データ不要）: (1) 点灯 — 調味料「持ってる」登録で解放される皿が光る（+1食材バンド） (2) 海岸線バッジ — 「あと食材1つで作れる」皿にマーク
- **ユーザー追加料理の配置**: 近傍k皿の固定座標の重み付き重心+衝突回避の微小ずらし。再計算なしで意味的に正しい位置に決まる。どのカタログ皿とも遠い異質料理は最寄り系統の島の外縁「開拓地」ルール
- 位置づけは従来通り**料理帳タブ内の1ページ**・3層構造（眺める→つまむ→決める）。3タブ構成（探す/ホーム/料理帳）維持
- **撤退線維持**: コンセプト画像でオーナーが「眺めたい・シェアしたい」と思えなければv1は地図なし（成長サマリで代替）

## 料理写真 — 欲望喚起側（未解決 → v2で方向確定）

役割分離により、未解決なのは**ホームおすすめカードの欲望喚起画像だけ**になった（記録側は上記「写真の扱い」で解決済み）。

- 確定した学習: AIは粒状食材（挽き肉・そぼろ・刻みねぎ）が構造的に苦手 / 不気味の谷はリアル度に比例し中間帯が最悪 / 料理ごとの実物参照なしでは崩れる
- **v2方針: 粒を描かない様式で絵に振り切る**。雑誌・デパ地下のフードイラストは、そぼろを粒で描き込まず「色面+数粒のアクセント」に抽象化するのが実務の様式。絵本調の失敗は「絵だから」ではなく「絵なのに写実の情報量を持たせようとした」から。再試作は実在フードイラストレーターの実例をスタイル参照に（design-research-first）、プロンプトに「粒状の質感を描き込まない」を明示、判定皿はガパオ
- 順序: claude.ai/designのUI生成が先（UIトーンと一体で判定精度が上がる）→ イラスト再試作
- **撤退線（写真にも切る）**: 再試作1ラウンドで不合格なら、v1は「記録側=写真ゼロ完成デザイン、欲望喚起側=紹介文の五感語に全振り」で出す。紹介文165件書き直しはこの保険として既に機能する品質

## 収益モデル（v2新設・オーナーGO 2026-07-04）

**設計原則: 買い切り=固定費ゼロ機能、従量=AIだけ。** 実行時AI原則（下記）が守られる限り、買い切りをいくら売っても原価は増えない。

- **無料** = コアループ全部（記録・おすすめ・料理帳・地図・当月の月次カード）+ キャプチャ月3回。資産形成を止めない — 堀が育たなくなるから記録と閲覧には課金しない
- **買い切りPro（¥1,800前後・一度きり）** = ローカル完結の永続機能: 料理帳カスタマイズ復活（表紙/フォント/スタンプ）・地図のポスター書き出し（高解像度、壁紙/印刷用）・料理帳の一冊書き出し（PDF、将来は製本連携）・月次カード全過去分+高解像度+デザインバリエーション・年間まとめ詳細版
- **キャプチャ回数券（消耗型、¥120で10回目安）** + ヘビー層向け月額¥300無制限（フェアユース上限付き）。解析原価は数円/回
- **課金導線 = 誇りの瞬間に売る**。インストール直後には出さない。出すのは3箇所: 4回目のキャプチャ / 月替わりで先月カードがアーカイブに入る瞬間（当月無料なので人質型にならない）/ 料理帳20品超えで「ここまで育った料理帳を、一冊に」。ポスターは透かし付きプレビューのみ無料
- **約束（binding）**: データ書き出し（素のバックアップ）は無料に残す。美しい版（PDF製本・ポスター）がPro。データそのものは常にユーザーのもの — 所有型の堀と矛盾させない
- 広告=不採用（滞在短く単価が出ず体験毀損のみ）。Fermi: 月480円系×転換3%×MAU1,400=月2万円ライン、必要DL累計約5,000。買い切りは累計転換5%で70人×¥1,800=約12.6万円（一過性）+新規流入比例。**年内の収益貢献は小さい**と明記（正月26万円目標はSleep Alarm等と合算で考える）

## 実行時AI原則（v2新設・binding）

**実行時にAIが動くのはキャプチャだけ。** カタログの紹介文・特徴量・近さスコアはビルド時の一回生産。推測通知=ヒューリスティクス、額縁=画像処理のみ、月次カード=テンプレ合成。この原則が収益モデルの前提。

## 制作フロー（binding — 2026-07-03の失敗から）
