# Spec 030: Experience Design — 体験設計の正本

Status: Draft（マップ2案の画像比較待ち）
Date: 2026-07-03（夜の壁打ち + カスタマイズ/マップリサーチ統合）
このspecはspec-029（視覚ディレクティブ）の上位。矛盾したらこちらが勝つ。

## 二本柱（全判断の基準）

レパートリー拡大の **コスト削減** × **モチベーション増加**。機能・画面・演出はどちらに効くかを明示できなければ入れない。

## アプリの本分

レシピ提供・調理のコツは主役にしない。「レパートリーを広げる」だけが主役。
例外: AI生成の詳しめレシピは全皿に同梱する（調べるのも面倒な人がここで完結するため。コスト削減側）。
最終目標（覚書）: レシピアプリ等との公式API連携によるレシピ取り込み。

## 画面ごとの体験定義

### ホーム — コスト削減
おすすめは少なく。シンプルで洗練。今日の一品が静かに1枚出ているだけでよい。
**構成の正本はNotion「おすすめ画面仕様書」（2026-06-13確定、ADR-005/spec-024に転記済み）**: ヘッダー→挨拶→難易度タブ（かんたん/少し広げる/しっかり作る、起点表示より上）→「この前作った『〇〇』から広げる」+他の起点にする→メインおすすめ1件→小カード3件。各カードに難易度ラベル必須、工程量は出さない。**コンセプト画像・実装とも難易度タブ+ラベルを落とさないこと**（2026-07-03: Codex画像がタブを描き落としオーナー指摘）。

### 探すタブ（旧・食材タブ） — コスト削減
「今すぐ何か作りたい人」の利便性特化。**検索は確定採用**: 料理名の部分一致検索+食材チップフィルタの2入口を1画面に。扱うのは**作った料理+ブックマークのみ**（全料理逆引きはしない）。食材ソートで即到達。料理カードは調理中でも見やすいこと。探索のコスト削減側の背骨は検索であり、マップではない。

### マップ — モチベ増加（冒険心）【条件付き採用: コンセプト画像判定待ち】
- 位置づけ: 「機能」ではなく**観賞+つまみ見ビュー**。下タブから外し、**料理帳タブ内の1ページ**として置く（自分の一冊をめくると自分の地図がある）
- 3層構造: **眺める層**（全体の絵。観賞・画像エクスポート・SNS共有）→ **つまむ層**（ノードタップ→下から写真+料理名+差分1行+所要時間のカード。欲望喚起の実働部隊はここ＝料理写真）→ **決める層**（詳しく見る→詳細画面）。覗けない地図は欲望を喚起しないため、タップ→カードだけは必須。食材管理等の操作は載せない
- マップが描くのは料理の宇宙ではなく**ユーザーのレパートリーグラフ**（ベース→となり関係のデータそのもの）。縦横無尽問題はデータ設計側の刈り込みで解決済み。複数ベースに繋がる料理は乗換駅として表現
- 霧・シルエット等の曖昧演出は**不採用**。「あれも作れる、これも作れそう」が**はっきり見える**
- 食材の点灯 — 食材を「持ってる」登録（探すタブ側の操作）→作れるようになる料理がマップ上で点灯（`new_ingredients`逆引き）
- 観賞価値の4条件: 自分の形をしている / 時間が刻まれている / 見るたび発見がある / 絵として美しい。前2つはデータ構造が自動で満たす。後2つがコンセプト画像の勝負
- ビジュアル候補: ~~A. 路線図 / B. 星座~~ **両案棄却（2026-07-03 オーナー判定）**。路線図=線が方向・進路の固定を暗示し「縦横無尽」に反する。星座=眺めたいと思えない。教訓: 様式から入らず、データの形（自分の料理が中心、方向を持たない放射・有機配置）から発想する。第3ラウンドは実例リサーチ→非方向性レイアウト案→Codex画像生成。オーナーが「眺めたい・シェアしたい」と思えなければ**v1はマップなしで出す**（撤退線は継続）
- タブ構成は**3タブに回帰**: 探す / ホーム / 料理帳（マップは料理帳内）

### 料理帳 — モチベ増加（達成感・所有感）【2026-07-04 全面改訂・オーナー承認】

**設計転換**: 料理帳に「こだわれる」層は既に他アプリ（れぴった等）にいる。狙うのは「記録が続かないが成長感はほしい」層。よって手動カスタマイズではなく**勝手に育っている体験**と**入力摩擦ゼロ**を中核にする。

原理: **中身入りで配られる料理帳**。れぴった型の弱点（登録するまで価値ゼロ）の逆を張る — 同梱データ（イラスト+紹介文+AIレシピ）があるから、「作った」1タップの瞬間に完成品のページが勝手に生まれる。ユーザーは一度も「書く」必要がない。編集は「できる」が「しなくても美しい」。

1. **1タップ記録**が唯一の入力（通知アクション/ホームカード直押し）
2. **自動昇格ランク**: 回数で 作った→定番→**十八番** が勝手に付く（手動スタンプ廃止）
3. **成長サマリ**: 料理帳を開くと先頭に差分1行（「今月+3品。揚げ物系が5品に」）— マップ不採用の代替は図でなく言葉と自動報酬
4. **月次サマリーカード自動生成**（「6月、新しく4品」1080×1080）— SNS共有資産。生のレシピ一覧は共有させない
5. **自作料理は名前1つで登録**→AIが紹介文・材料・レシピ下書きを自動生成して埋める。将来: YouTube URL貼るだけでカード自動生成（メタデータ+埋め込みの範囲）

**v1から外す**（旧5機能のうち）: 表紙ピッカー / コレクション命名 / 手書き風フォント / 手動スタンプ30〜50種。残すのは**写真差し替えのみ**（こだわりではなく自分の記録なので）。
カードの中身: 差分説明+AIレシピ+YouTube/URL添付+自分メモ+編集上書き。他サイト本文の自動転載は権利面で不可。

**品質の考え方（オーナー確定 2026-07-04）**: AIレシピは「それなり」でよい（下書きと明示）。**品質は外部から持ってくるのが勝ち方** — YouTube埋め込みとユーザー自身の編集が品質保証の実体。

### 料理写真 — モチベ増加【確定プラン 2026-07-03】
作りたい気持ちの主要源泉として重視。プロ発注は1カット1〜3万円×120皿=120〜360万円で不可。確定フロー:
1. **スタイルガイド固定**（`docs/marketing/tonari-photo-trial-prompts.md`）— 全皿共通の構図・光・器・背景トーン
2. **5皿試作**: GPT画像生成（本人のChatGPT UI、プラン内で無料）でスタイルガイド準拠の5枚→オーナーの「うまそう」判定
3. **判定OK→全皿一括生成**: 採用料理確定後（レビュー完了後）に一括。手段はChatGPT UI手作業（無料・数時間）かOpenAI画像API（≈¥1,500〜4,000・自動）を試作結果を見て選択
4. 判定NG→スタイル修正で再試作（2回まで）。それでもNGなら統一イラスト路線に切替
**2026-07-03追記**: Codex生成のコンセプト画像内の実写風料理写真にオーナーが不気味の谷を指摘（「AIが作った料理写真って得体のしれない気持ち悪さ」「そのまま採用することはできない」）。実写リアル路線は不気味の谷リスクが構造的に高いため、**統一イラスト/水彩/版画調トーンの試作を第一候補に格上げ**して5皿試作を行う（実写風と並走比較でも可）。配布=絵、ユーザー差し替え=実写真、の対比はむしろ所有感演出に効く。
**2026-07-04追記**: 水彩イラスト（round 3）も「いいけどまだ不気味の谷」判定。二方向で並走試作する: **(a) 実写参照で寄せる** — 実際の家庭料理写真を参照画像にして生成し「AIっぽさ」を消せるか（スマホ実写風・完璧すぎない盛り付けも試す）/ **(b) 絵に振り切る** — デフォルメ強めの絵本調フラット・線画+単色。不気味の谷はリアル度に比例するため中間帯（今の水彩）が最も危険。
**2026-07-04スタイル試作判定（オーナー）**: 線画=却下（気持ち悪い）。絵本調=肉じゃがは悪くないがガパオがNG — **AIはそぼろ・挽き肉等の粒状食材の描画が苦手**（肉が気持ち悪く見える主因）。スマホ実写風=肉じゃがは多少良いがガパオはうまそうに見えない。→次段: **オーナー提供の実物写真（ガパオ3枚・肉じゃが3枚、`mocks/photo-refs/`）を参照画像にした生成**で谷を越えられるか検証。テスト皿は粒状食材のガパオが基準。
**ホームのトーン判定（2026-07-04確定）**: **mid（クリーム基調のまま明度・彩度を一段上げた中間トーン）が本命** — オーナー・Fable一致。以後のUI生成はhome-mid.pngのトーンを基準にする。
**UI制作手段の判定（2026-07-04夜・最終）**: home-mid.png（Codex画像）も home-html.html（Fable手組みHTML）もオーナー不合格（AI臭・雰囲気）。**UIはclaude.ai/designで生成する路線に確定**。手順はメモリ`reference-claude-design`参照（アンケート追加メモ欄にHex/画面名/仕様を全部書く・1回5画面まで・PNGはスクショ保存）。
**実写参照試作の判定（2026-07-04夜・最終）**: photo-ref-gapao/nikujaga（実物写真3枚ずつ参照）もオーナー不合格「なんかダメ」。フォー・油淋鶏（スタイル参照のみ）はさらに劣化（フォーの肉がハチの巣状、粒状食材の均質化再発）。**料理写真の方向は未解決** — 残る選択肢: (a) claude designでUIと一体の写真トーンを探る (b) イラストの別スタイル再試作 (c) フリー実写素材(ストックフォト)の直接利用 (d) 写真なしデザイン。次セッションでオーナーと決める。
5. 配布写真はユーザー撮影写真で差し替え可能（DishOverride表紙写真フィールド）。保存はファイルシステム、AsyncStorage不可
判定OKの時点でADR-007の「写真なし」を改訂。

### タブ構成
3タブ理想だが、料理帳の役割が厚くなったため**4タブ（食材/ホーム/マップ/料理帳）を有力案**とする。各タブ=1感情（利便/今日/冒険/所有）。コンセプト画像を見て最終決定。

## 制作フロー（binding — 2026-07-03の失敗から）

リサーチ→**コンセプト画像生成→オーナーが納得するまで選び直し**→`codex exec -i`で画像添付実装。文章のみのUI委任は禁止。

## データ構造の監査結果（2026-07-03、実データ検証済み）

1. **【重大】星型1ホップ問題**: v3の52関係は全て ベース→となり の一方向で、となり起点の関係・乗換駅（複数ベース→同一料理）がゼロ。起点昇格してもその先の道がない。対策: 人気となり20〜30皿を準ベースとし第二階層関係（各4〜6件）をデータ拡充に追加+乗換駅を意図的に張る【**採用確定** 2026-07-03「妥協なし」方針。v4bレビュー後に準ベース選定→第三弾生成】
2. **【中】食材マスタ正規化**: 現76食材は生文字列（今は表記ゆれなし）。マップ点灯は文字列一致依存のため、マスタ（id+表示名）化し以後の生成はマスタ参照必須にする
3. **【中】写真ストレージ**: ユーザー写真差し替えを入れる場合、ネイティブはAsyncStorage base64不可→expo-file-system+パス参照。Web版のbase64 localStorageも同様の限界あり
4. **【小】dish_id不変契約**: ユーザーデータは全てdish_idキー。データ更新でidを変えない契約を明文化
5. **【小】同梱サイズ**: AIレシピtext=問題なし（~240KB）。写真120枚は同梱かリモート配信かを試作後に判断

### 検索スコープ（提案中）
探すタブの検索対象は**自分のレパートリー内のみ**（作った+ブックマーク+自作の料理名検索）。カタログ全体検索はv1では入れない — 「探さなくても出てくる」の本分を守る。新規発見はホーム提案+マップ点灯の2経路。

### 写真の所有権設計（確定）
配布写真（AI生成）はユーザー撮影写真で差し替え可能にする（DishOverrideに表紙写真フィールド追加）。「配られた写真が自分の写真に置き換わっていく料理帳」= 所有感の中核演出。

## 紹介文ルール改訂（2026-07-03）

正本はNotion「おすすめ画面仕様書」§13（1行目=味の変化 / 2行目=タブ別に作りやすさ・食べる場面・ごちそう感）。これに以下を追加:
- **未知料理の正体先行**: 日本の家庭で馴染みの薄い料理は1行目で「どういう料理か」を先に置く（例:「バジルとナンプラーの香りで食欲直撃、タイの甘辛炒めごはん。」）。既知料理は従来通り味の変化のみでよい
- 1行目には五感に訴える具体語を必ず1つ以上（じゅわっと・香ばしい・とろける等）
- 禁止: 差分メモ調（「〜は変わらない」「〜と同じ工程」）、抽象語単独（美味しい・本格的）、材料の羅列
- 失敗記録: candidates-v4/v4bの生成プロンプトが正本ルールを参照せず「what stays the same / no marketing fluff」で生成→165件全滅。**紹介文を生成する全プロンプトに本ルールを逐語で埋め込むこと**
