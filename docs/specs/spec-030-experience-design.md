# Spec 030: Experience Design — 体験設計の正本

Status: Draft（マップ2案の画像比較待ち）
Date: 2026-07-03（夜の壁打ち + カスタマイズ/マップリサーチ統合）
このspecはspec-029（視覚ディレクティブ）の上位。矛盾したらこちらが勝つ。

## 二本柱（全判断の基準）

レパートリー拡大の **コスト削減** × **モチベーション増加**。機能・画面・演出はどちらに効くかを明示できなければ入れない。

## アプリの本分

レシピ提供・調理のコツは主役にしない。「レパートリーを広げる」だけが主役。
例外: AI生成の詳しめレシピは全皿に同梱する（調べるのも面倒な人がここで完結するため。コスト削減側）。
最終目標（覚書）: レシピアプリ等との公式API連携によるレシピ取り込み。

## 画面ごとの体験定義

### ホーム — コスト削減
おすすめは少なく。シンプルで洗練。今日の一品が静かに1枚出ているだけでよい。

### 探すタブ（旧・食材タブ） — コスト削減
「今すぐ何か作りたい人」の利便性特化。**検索は確定採用**: 料理名の部分一致検索+食材チップフィルタの2入口を1画面に。扱うのは**作った料理+ブックマークのみ**（全料理逆引きはしない）。食材ソートで即到達。料理カードは調理中でも見やすいこと。探索のコスト削減側の背骨は検索であり、マップではない。

### マップ — モチベ増加（冒険心）【条件付き採用: コンセプト画像判定待ち】
- 位置づけ: 「機能」ではなく**観賞+つまみ見ビュー**。下タブから外し、**料理帳タブ内の1ページ**として置く（自分の一冊をめくると自分の地図がある）
- 3層構造: **眺める層**（全体の絵。観賞・画像エクスポート・SNS共有）→ **つまむ層**（ノードタップ→下から写真+料理名+差分1行+所要時間のカード。欲望喚起の実働部隊はここ＝料理写真）→ **決める層**（詳しく見る→詳細画面）。覗けない地図は欲望を喚起しないため、タップ→カードだけは必須。食材管理等の操作は載せない
- マップが描くのは料理の宇宙ではなく**ユーザーのレパートリーグラフ**（ベース→となり関係のデータそのもの）。縦横無尽問題はデータ設計側の刈り込みで解決済み。複数ベースに繋がる料理は乗換駅として表現
- 霧・シルエット等の曖昧演出は**不採用**。「あれも作れる、これも作れそう」が**はっきり見える**
- 食材の点灯 — 食材を「持ってる」登録（探すタブ側の操作）→作れるようになる料理がマップ上で点灯（`new_ingredients`逆引き）
- 観賞価値の4条件: 自分の形をしている / 時間が刻まれている / 見るたび発見がある / 絵として美しい。前2つはデータ構造が自動で満たす。後2つがコンセプト画像の勝負
- ビジュアル候補（画像比較で決定）: **A. 路線図** / **B. 星座**。オーナー（+可能なら友人）が「眺めたい・シェアしたい」と思えなければ**v1はマップなしで出す**
- タブ構成は**3タブに回帰**: 探す / ホーム / 料理帳（マップは料理帳内）

### 料理帳 — モチベ増加（達成感・所有感）
リサーチ結論「組み立てが愛着を生む・選択肢は5〜8個に厳選・輸入+写真+自分メモの混在が『自分のもの』感を作る」に基づく:
1. 表紙ピッカー（8〜12種、静的アセット）
2. コレクション自分命名
3. マイルストーン画像エクスポート（「2026年、42品作った」1080×1080。生のレシピ一覧は共有させない — 集計カードだけ共有可能に）
4. 手書き風フォント3〜5種
5. スタンプ/シール30〜50種（作った記録に押す。御朱印的演出はここ）
カードの中身: 差分説明+AIレシピ+YouTube/URL添付+自分メモ+編集上書き。他サイト本文の自動転載は権利面で不可。

### 料理写真 — モチベ増加【確定プラン 2026-07-03】
作りたい気持ちの主要源泉として重視。プロ発注は1カット1〜3万円×120皿=120〜360万円で不可。確定フロー:
1. **スタイルガイド固定**（`docs/marketing/tonari-photo-trial-prompts.md`）— 全皿共通の構図・光・器・背景トーン
2. **5皿試作**: GPT画像生成（本人のChatGPT UI、プラン内で無料）でスタイルガイド準拠の5枚→オーナーの「うまそう」判定
3. **判定OK→全皿一括生成**: 採用料理確定後（レビュー完了後）に一括。手段はChatGPT UI手作業（無料・数時間）かOpenAI画像API（≈¥1,500〜4,000・自動）を試作結果を見て選択
4. 判定NG→スタイル修正で再試作（2回まで）。それでもNGなら統一イラスト路線に切替
5. 配布写真はユーザー撮影写真で差し替え可能（DishOverride表紙写真フィールド）。保存はファイルシステム、AsyncStorage不可
判定OKの時点でADR-007の「写真なし」を改訂。

### タブ構成
3タブ理想だが、料理帳の役割が厚くなったため**4タブ（食材/ホーム/マップ/料理帳）を有力案**とする。各タブ=1感情（利便/今日/冒険/所有）。コンセプト画像を見て最終決定。

## 制作フロー（binding — 2026-07-03の失敗から）

リサーチ→**コンセプト画像生成→オーナーが納得するまで選び直し**→`codex exec -i`で画像添付実装。文章のみのUI委任は禁止。

## データ構造の監査結果（2026-07-03、実データ検証済み）

1. **【重大】星型1ホップ問題**: v3の52関係は全て ベース→となり の一方向で、となり起点の関係・乗換駅（複数ベース→同一料理）がゼロ。起点昇格してもその先の道がない。対策: 人気となり20〜30皿を準ベースとし第二階層関係（各4〜6件）をデータ拡充に追加+乗換駅を意図的に張る【**採用確定** 2026-07-03「妥協なし」方針。v4bレビュー後に準ベース選定→第三弾生成】
2. **【中】食材マスタ正規化**: 現76食材は生文字列（今は表記ゆれなし）。マップ点灯は文字列一致依存のため、マスタ（id+表示名）化し以後の生成はマスタ参照必須にする
3. **【中】写真ストレージ**: ユーザー写真差し替えを入れる場合、ネイティブはAsyncStorage base64不可→expo-file-system+パス参照。Web版のbase64 localStorageも同様の限界あり
4. **【小】dish_id不変契約**: ユーザーデータは全てdish_idキー。データ更新でidを変えない契約を明文化
5. **【小】同梱サイズ**: AIレシピtext=問題なし（~240KB）。写真120枚は同梱かリモート配信かを試作後に判断

### 検索スコープ（提案中）
探すタブの検索対象は**自分のレパートリー内のみ**（作った+ブックマーク+自作の料理名検索）。カタログ全体検索はv1では入れない — 「探さなくても出てくる」の本分を守る。新規発見はホーム提案+マップ点灯の2経路。

### 写真の所有権設計（確定）
配布写真（AI生成）はユーザー撮影写真で差し替え可能にする（DishOverrideに表紙写真フィールド追加）。「配られた写真が自分の写真に置き換わっていく料理帳」= 所有感の中核演出。

## 実装済み資産との関係

web-v29ブランチの機能層（DishOverride/CustomDish/データ構造/計測）は全て存続。作り替えるのは見た目と、マップのビジュアル全面刷新+食材点灯機構の追加。
