## Phase A-0 — 生語彙の抽出（実施済み 2026-07-17）

282皿（当時）を6分割し、Sonnetエージェント6本が**統制なしで**素直に材料・調味料・調理法・役割タグ・工程数を列挙。
「正規化するな・同義語を畳むな・最も自然な具体名を書け（豚バラ肉であって豚肉ではない）」を制約に、
語彙の自然分布を可視化することだけが目的。調理法はv2語彙を提示しつつ**足りなければ発明してよい**とした
（発明された語＝v2語彙の穴の発見）。

|---|---|---|

## Phase A-1 — 凍結（オーナー＋オーケストレーター）

A-0の生語彙をクラスタリングして畳む／残すを決める。**判断の対象は「70語前後の畳み方」の一点**。

### 粒度の原則: 頻度の逆を取る

パイロット実測が根拠。醤油は25皿中14皿に出現し、IDF重みが既にほぼゼロまで潰している。
**ここで醤油を濃口/薄口/たまりに割ると、IDFが人為的に上がり、本来ノイズだったものが票を持ち始める**。
逆に豆板醤は1皿のみ＝麻婆豆腐の正体そのもので、味噌に畳んではならない。

> **ありふれた語ほど粗く、珍しい語ほど細かく。**
> 判定基準は「この統合で皿の正体が変わるか」であって頻度単独ではない。

**訂正（2026-07-17、GPTレビュー）**: 初版はここに「ありふれた語を畳むのはIDFがどうせ潰すのでタダ」と
書いていたが**二重に誤り**。(a) 醤油のIDFは0.61で0ではない（初版の「ほぼ0」はスクリプトのリテラル0を
印字して信じた捏造値）。(b) より重要な誤りとして、**畳むコストはありふれた側ではなく珍しい側にある**。
薄口醤油は7皿のみ＝単独ならIDF 3.7の強い証拠だが、醤油へ畳むとその7皿は互いを3.7で見つける代わりに
154皿の海に0.61で溶ける。表記ゆれ（出汁→だし）の統合は依然タダだが、機能差のある語の統合は損失を伴う。
この誤りは実害を出した — 骨付き・塊肉まで畳んだ結果、唐揚げと手羽先の唐揚げのレコードが完全一致した。

### 凍結物（`data/vocab/aliases.json` — オーナーの拒否権はここ）

- 調味料の別名テーブル + 複合語の分割（塩こしょう → 塩 + こしょう）
- 食材マスタ。**薄切り・こま・切り方だけ畳む。骨付き・内臓・塊肉は畳まない**。魚は種を保持
- 調理法語彙（36語）+ **主技法の優位順位**（`method_dominance`）
- 役割 7種（main/sub/coat/bind/thicken/base/**とじ**）

### 層分離（2026-07-17、オーナー指摘）

**畳み込みはデータ加工ではなく採点時の変換**。`dish-v4-281.json` は皿の実体（表示の正）を持ち、
豚の角煮は `豚バラ肉(ブロック)` のまま。`proximity_281.py` が読み込み時に `seas_c`/`ing_c` を別途構築する。
紹介文・冷蔵庫マッチング・財布度の根拠は全て部位を要求するので、データ側を畳んではいけない。

### A-2. Dish v4 スキーマ確定版

パイロットv2で実証済みの構成を確定させる。

| フィールド | 内容 | 出所 |
|---|---|---|
| box / tier | 7箱タクソノミ / S・A・B | 既存 |
| ingredients | **生の食材名**（豚バラ肉(ブロック)）+ 役割タグ7種。畳まない | v2修正2 + 07-17層分離 |
| seasonings | **生の調味料名**（薄口醤油）。畳まない | v2修正1 + 07-17層分離 |
| methods | 細分化語彙（36語） | v2修正5 |
| primary_method | 主技法（`method_dominance` の最強語）。仕上がりを決める技法 | **07-17新設** |
| steps | 工程数 2〜8。**スコアには使わない** | パイロット |
| effort | 背伸び度prior 1〜3 | パイロット |
| cost | 財布度 1〜3 | v2修正6 |
| derived_from | 派生エッジ（カツ丼⊃とんかつ）。近さと別チャネル | v2修正4 |

**スコア式**: `0.500×調味料 + 0.333×食材 + 0.167×調理法`（各Dice、IDF重み付き、無向、和1.00）
- **工程軸は削除**（07-17）。共通技術ゼロの皿の間に溜まるベースラインだった（ハンバーグ↔とんかつ 0.04→0.00）
- 旧 0.45/0.30/0.15/0.05 は**和が0.95**でスコア上限が1.0に届かず、raw scoreの閾値が最初から狂っていた
- **比率45:30:15は281皿で未検証**（Q2として開けてある）

**プール分割**: 副菜・汁ものは自プール内のみ。主菜↔ごはん麺クロスは×0.75減衰。
**cost / steps はスコアに入れない**。

**推薦ゲート（スコアと分離）**: `score >= 0.30 かつ 根拠 >= 2件`。
根拠 = 主素材の共有 / 主技法の一致 / 調味料×主技法のパターン一致。工程の近さと副材料1個は根拠に数えない。
スコアは「どれだけ重なるか」、根拠は「腕が移る理由があるか」で、両者は乖離する（ロールキャベツと
かぼちゃのポタージュは `{コンソメ}` 同士でDiceが比率ゆえIDFが相殺されて調味料軸1.00、しかし根拠は0件）。
**地図は無向・ゲート無しの素の近さを使う。ゲートはホーム推薦だけ。**

### A-3. 入り口皿リスト（確定 2026-07-18）

**役割**: 紹介文の書き方をここだけ場面型（「疲れた夜に」等）にしていい特別枠。他の皿は料理実体型で書く。
**選定基準**: 想定ユーザー（料理をこれから始める〜数年目の一人暮らし層）が実際に最初に作る主菜。
副菜・汁物・おともは対象外（食事の中心にならないため、主菜レパートリー拡張のアンカーにならない）。
主菜3箱（`主菜(肉)` / `主菜(魚介)` / `ごはんもの+麺類`）のtier=Sから、初心者が実際に作る枠に絞る。

  - 除外: とんかつ（衣揚げは唐揚げより一段上）、すき焼き（鍋・場面料理）

## Phase B — 量産（Codex委任、M5=282件で CODEX案件）

Phase Aの凍結物を入力に、機械的に回す。設計は2026-07-18のadvisor相談で確定
（`docs/advisor-brief-2026-07-18-phase-b-format.md` / `docs/advisor-out-2026-07-18-phase-b-format.txt`）。

### B-0. 分担（重要）

**Codexには紹介文だけ書かせる**。特徴量（seasonings/ingredients+roles/methods/primary_method/steps 等）は
`data/vocab/dish-v4-281.json`が正で、Codexに再生成させない。特徴量と紹介文の結合は`scripts/`側で機械的に行う。

Codexに特徴量を書き直させると、①凍結済み・検証済みのデータをCodexが微妙に改変するリスクが最大の失敗モードになる
（advisor Q4）、②A-0→A-1で組んだ語彙凍結の意味が薄れる。分担を明示的に切ることで、Codexの得手（自然言語生成）に
仕事を寄せ、Codexの不得手（大量の構造化データの完全性維持）を機械側で受ける。

### B-1. 出力フォーマット

**中間: `data/v4-intros.json`** — Codex生成物。皿名→intro_line1/intro_line2 の対応表のみ:

```json
[
  {"name": "肉じゃが", "intro_line1": "...", "intro_line2": "..."},
  ...
]
```

**最終: `data/v4-dishes.json`** — 結合済み。Dish v4スキーマ + intro 2フィールド:

```json
[
  {
    "name": "肉じゃが",
    "seasonings": [...], "ingredients": [{"name":"...", "role":"..."}, ...],
    "methods": [...], "primary_method": "...", "steps": ...,
    "box": "...", "tier": "...",
    "intro_line1": "...", "intro_line2": "..."
  },
  ...
]
```

`generated_at`やハッシュはCodex出力に含めない（必要なら`scripts/`側で決定的に付与）。
`data/v3.ts`は今回のspecでは触らない（消費コード16箇所を巻き込むため別goal＝引継ぎNext 2）。

### B-2. 実行単位

**7バッチに分割**。1バッチ1 codex exec。

- **バッチ0**: 入り口皿17皿（A-3）— 紹介文の**場面型**（1行目のみ場面型、2行目は作る側の現実）。この形式は他バッチと文法が違うので専用バッチにして例文もこのバッチ専用に固定
- **バッチ1〜6**: 残り265皿を約44皿×6バッチ（46/44/44/44/44/43 等の等分割）。**料理実体型**（基調）

コンテキスト上限より、長大な構造化出力の欠落・形式崩れ・文体劣化のリスクが支配的、というadvisorの判断。
プロンプトと模範例は各バッチで固定し、期待する皿名リストをバッチ毎に明示してCodex出力と機械照合する。

### B-3. 検証（結合前ゲート）

Codex出力`data/v4-intros.json`を`data/v4-dishes.json`に結合する前に、以下の4種の機械チェックを全て通す:

1. **皿名の集合一致**: `dish-v4-281.json`の全282皿名 == 各バッチのintroを合わせた集合。過不足ゼロ
2. **重複検査**: 同一皿名が複数回登場しない
3. **文字列類似度**: 全intro_line1同士・intro_line2同士のJaccard/編集距離で「事実上同一の紋切り型」を検出。閾値0.85超は差し戻し対象（機械的に近い文が皿を跨いで生成されがち、advisor Q4）
4. **語彙外検査**: intro文中に、`aliases.json`の外の食材・調味料名が出ていないか（例: 「鶏もも肉」は正、「チキン」は外の可能性）。ゆるい正規表現で十分、完全一致は求めない

結合後の`data/v4-dishes.json`に対しては追加で:

5. **特徴量の不変性**: 結合後の各皿のDish v4フィールドが`dish-v4-281.json`と完全一致

いずれか失敗 → 当該バッチのみ再実行（既に通ったバッチは温存）。

### B-4. 制約（変わらず）

**語彙は凍結済み。語彙外の語は出力できない**。A-0が全282皿を舐めた上で語彙を作っているので、
ここで語彙の穴が出るのは想定外事象＝報告対象（初版のような差し戻しループは前提にしない）。

模範例は再著作しオーナー承認済み: `docs/decisions/2026-07-18-tonari-intro-exemplars.md`

## Verification（281皿は目視できない。機械ゲートで受ける）— **実施済み、全て通過**

25皿はオーナーの目視で検証したが、281皿では不可能。`scripts/proximity_281.py` を全量で実行。

**回帰（維持されるべき）** — v2の良好ペアが全量でも保持されること:
唐揚げ↔竜田揚げ / とんかつ↔あじフライ / 親子丼↔カツ丼 / 豚汁↔けんちん汁 / ハンバーグ↔煮込みハンバーグ / 生姜焼き→ぶり照り・鮭照りがTOP2 / さばの味噌煮→肉じゃが

**抑制（沈んだままであるべき）** — v1の違和感5ペア:
生姜焼き→カツ丼 / 唐揚げ→麻婆豆腐 / チャーハン→ニラ玉 / ハンバーグ→とんかつ（チャーハン→けんちん汁は別プールで対象外）

**スケール解消の賭け（v2で「282皿で自然解消する」と判断した項目 — 外れたらスキーマをもう1周）**:
- チャーハン→ニラ玉が1位から落ちる（天津飯・かに玉・オムライスが入るため）
- ハンバーグ→とんかつがさらに沈む（フライ系20皿超でソースのIDFが下がるため）
- 焼きそば・ナポリタンの孤立が解消（お好み焼き・とん平焼き・オムライス・ミートソースと繋がる）
- 副菜プール内の近さが成立（副菜26＋煮物4で初めて検証可能）
- 調味料1〜2個の皿（鮭の塩焼き・焼きそば）が低スコアに張り付かない（必要ならoverlap係数とブレンド）

これらは「自然解消するはず」の**賭け**であって確認済み事実ではない。**外れた場合は失敗チェックとして表面化させ、黙って通さない。**
→ **5件とも的中**。ただし「調味料1〜2個の皿」は読み違いで、実体は逆向き（小集合が満点を出す）だった。
