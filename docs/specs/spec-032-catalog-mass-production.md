## 構造：3ステップ。Phase BはPhase Aの出力に完全に従属する

パイロットの最大の発見は「別名テーブルは前提条件」（v1分析5）。**Codexが生成中に語彙を発明すると、v2で潰したノイズがそのまま再発する**。したがって語彙を凍結してからでないと量産は走らせられない。この依存が本specの背骨。

ただし**282皿の中身を見ずに語彙を列挙することはできない**（鶏と卵）。初版の「語彙外の語が出たら差し戻す」という制約は、この鶏卵をループで解こうとしていた。抽出パスを1段前に置いて解消する。

- **A-0 抽出**（機械的・安いモデル）— 正解が皿の中にあるので判断不要
- **A-1 凍結**（判断・オーナー＋オーケストレーター）— 唯一の高判断
- **B 生成**（Codex）— 凍結語彙に従属。語彙外は出ようがない

## Phase A-0 — 生語彙の抽出（実施済み 2026-07-17）

282皿を6分割し、Sonnetエージェント6本が**統制なしで**素直に材料・調味料・調理法・役割タグ・工程数を列挙。
「正規化するな・同義語を畳むな・最も自然な具体名を書け（豚バラ肉であって豚肉ではない）」を制約に、
語彙の自然分布を可視化することだけが目的。調理法はv2語彙を提示しつつ**足りなければ発明してよい**とした
（発明された語＝v2語彙の穴の発見）。

### A-0 の結果 **[集計待ち]**

### 事前見積もり（パイロット25皿からの外挿）

25皿で調味料17語・食材35語・調理法10語。Heapsの法則（V≈K·N^β）で282皿なら調味料55〜75語。
パイロットは和食定番に偏っており、282皿にはカレー・エスニック・イタリアンの裾（ナンプラー・
オイスターソース・豆板醤・バジル・サフラン・クミン）が付くので、**実際は70語前後**が見込み。
**初版の目標値「30〜50語」は下方に外れている見込み** — 押し込むと本来分けるべき語を潰すことになる。
語彙数は目標値ではなく皿から積み上がった結果として決まる。

## Phase A-1 — 凍結（オーナー＋オーケストレーター）

A-0の生語彙をクラスタリングして畳む／残すを決める。**判断の対象は「70語前後の畳み方」の一点**。

### 粒度の原則: 頻度の逆を取る

パイロット実測が根拠。醤油は25皿中14皿に出現し、IDF重みが既にほぼゼロまで潰している。
**ここで醤油を濃口/薄口/たまりに割ると、IDFが人為的に上がり、本来ノイズだったものが票を持ち始める**。
逆に豆板醤は1皿のみ＝麻婆豆腐の正体そのもので、味噌に畳んではならない。

> **ありふれた語ほど粗く、珍しい語ほど細かく。**
> ありふれた語を畳むのはIDFがどうせ潰すので**タダ**。慎重さを要するのは珍しい側だけ。
> v1の失敗（ありふれた調味料が皿の正体と同じ票を持つ）はこの原則の裏返しで、v2はIDFで対症療法をした。
> 語彙設計でも同じ原則を通せば二重に効く。

### 凍結物

- 調味料語彙 + 別名テーブル（カレールー/カレー粉→カレー 等）
- 食材マスタ（肉は蛋白ファミリーに畳む、魚は種を保持 — 魚種の乗り換えがフロンティアそのものなので）
- 調理法語彙 — **閉じた集合。282皿でも12〜15語にしかならず、v2で細分化済み。ほぼ完成しており先に凍結可能**

### A-2. Dish v4 スキーマ確定版

パイロットv2で実証済みの構成を確定させる。

| フィールド | 内容 | 出所 |
|---|---|---|
| box / tier | 7箱タクソノミ / S・A・B | 既存 |
| main_ingredients | 正規化語彙 + **役割タグ**（main/sub/coat/bind/thicken/base） | v2修正2 |
| seasonings | 正規化語彙（別名テーブル適用済み） | v2修正1 |
| methods | 細分化語彙 | v2修正5 |
| steps | 工程数 2〜8 | パイロット |
| effort | 背伸び度prior 1〜3 | パイロット |
| cost | 財布度 1〜3 | v2修正6 |
| derived_from | 派生エッジ（カツ丼⊃とんかつ）。近さと別チャネル | v2修正4 |

**スコア式（凍結）**: `0.45×調味料 + 0.30×食材 + 0.15×調理法 + 0.05×工程`（各Dice、IDF重み付き、無向）
**プール分割**: 副菜・汁ものは自プール内のみ。主菜↔ごはん麺クロスは×0.75減衰。
**cost はスコアに入れない**（消費者は週セット予算レンズ・reasonチップ・紹介文の代替表記）。

## Verification（284皿は目視できない。機械ゲートで受ける）

25皿はオーナーの目視で検証したが、284皿では不可能。`scripts/proximity_pilot.py` を全量で再実行し、以下をアサートする。

**回帰（維持されるべき）** — v2の良好ペアが全量でも保持されること:
唐揚げ↔竜田揚げ / とんかつ↔あじフライ / 親子丼↔カツ丼 / 豚汁↔けんちん汁 / ハンバーグ↔煮込みハンバーグ / 生姜焼き→ぶり照り・鮭照りがTOP2 / さばの味噌煮→肉じゃが

**抑制（沈んだままであるべき）** — v1の違和感5ペア:
生姜焼き→カツ丼 / 唐揚げ→麻婆豆腐 / チャーハン→ニラ玉 / ハンバーグ→とんかつ（チャーハン→けんちん汁は別プールで対象外）

**スケール解消の賭け（v2で「282皿で自然解消する」と判断した項目 — 外れたらスキーマをもう1周）**:
- チャーハン→ニラ玉が1位から落ちる（天津飯・かに玉・オムライスが入るため）
- ハンバーグ→とんかつがさらに沈む（フライ系20皿超でソースのIDFが下がるため）
- 焼きそば・ナポリタンの孤立が解消（お好み焼き・とん平焼き・オムライス・ミートソースと繋がる）
- 副菜プール内の近さが成立（副菜26＋煮物4で初めて検証可能）
- 調味料1〜2個の皿（鮭の塩焼き・焼きそば）が低スコアに張り付かない（必要ならoverlap係数とブレンド）

これらは「自然解消するはず」の**賭け**であって確認済み事実ではない。**外れた場合は失敗チェックとして表面化させ、黙って通さない。**
