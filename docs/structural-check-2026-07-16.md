# tonari-app 構造チェック — 2026-07-16

Claude によるコード＋ランタイム構造チェック（UI人間監査はオーナーが別途実施）。実機: `npm run dev` @ localhost:3000、全画面巡回。

## 通底する結論

発見の大半（2・3・4・5）は**アプリのデータ層がカタログ再構築前のまま**であることに起因する。アプリは旧モデル（base 10 → target 52 の手書きエッジ、計62皿）を配信中で、251皿トップダウンの新カタログは未実装。つまり判定シートで×にする産廃が、今まさにアプリの本体カタログになっている。→ カタログ確定（タスク1）が、これらデータ起因バグの大半のアンロック。

## 発見

### 1. `.next` キャッシュ破損404（環境・コード非依存）＝要恒久対策
このセッションだけで2回踏んだ。1回目は全画面404、2回目はサーバー再起動後に `/dish/[id]` ルートだけ404（`/home`・`/search` は200なのに詳細だけ落ちる紛らわしい出方）。いずれも `.next` 削除＋再起動で復旧。原因は既知の「検証用 `npm run build` と dev サーバーが同一 `.next` を奪い合う」地雷。手動掃除の繰り返しは非効率なので、**恒久対策**（build 用に別ディレクトリ `distDir`、または dev 中は build を打たない運用ガード）を推奨。

### 2. データ層がカタログ再構築前（最重要・データ同期タスク）
`data/v3.ts` の配信52 target に脱落候補・産廃が多数実在: マーボーカレー / 肉じゃがコロッケ / カレーパン風揚げパン / 炊き込みチャーハン風 / パッタイ風米麺炒め / あんかけ焼きそば / カレー焼きそば / ナポリタンピザトースト / 焼きそばパン / 焼きそばオムレツ / 親子うどん / 水炊き風親子鍋 / 簡単パエリア風 / サーモンチャーハン / キムチチャーハン / レモンクリームパスタ 等。カタログ確定後に `data/v3.ts` を新カタログで作り直す必要。

### 3. genre誤判定で主菜・産廃が「あと一品」に出る
料理詳細の「あと一品」は `genreForDish` が 'side'/'soup' の料理を拾う（`DishDetailScreen.tsx:47`）。だが62皿に本物の副菜が無いため、スープカレー・カレーパン風揚げパン・麻婆鍋を誤って副菜・汁もの扱いにして表示。→ 再構築でおとも層を足せば解消。

### 4. オンボーディング候補がハードコード（2026-07-16 一部修正済み）
`OnboardingScreen.tsx:10` の `ONBOARDING_IDS` に pad-thai（パッタイ＝産廃）が固定されていた。**修正済み**: pad-thai を削除（16→15件、3列グリッドが5行ちょうど）。置換でなく削除としたのは料理選定=オーナー領分のため。実機確認済み（15枚・パッタイ消滅）。残: `INITIAL_SELECTION`（3品デフォルト選択）はキャンバス原案=全未選択との差分で、要否をオーナー確認（引き継ぎ書 Next #3）。カタログ確定後は候補リスト全体を新カタログで作り直すのが本筋。

### 5. 検索の食材チップがセマンティクスずれ
チップは「レパートリー料理そのものの主材料」でなく「近隣バリエーションが新たに導入する食材（`relations.new_ingredients`）」から導出（`SearchScreen.tsx:48-65, 172-186`）。結果、3皿レパートリー（チャーハン/唐揚げ/肉じゃが）のどれもごぼうを使わないのに「ごぼう」チップだけ出る（筑前煮・炊き込みチャーハン風という"隣"がごぼうを使うため）。2026-07-13決定「レパートリーの主材料で絞る」と噛み合っていない。食材データ再構築時に見直し。
