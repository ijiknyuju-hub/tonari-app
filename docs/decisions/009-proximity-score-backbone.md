# ADR-009: Proximity Score as Data Backbone

- **Title**: Replace hand-curated base→tonari edges with feature-derived proximity scores
- **Context**: v3's 52 relations were all one-directional (base→tonari), creating the star/1-hop problem: no paths beyond the first hop, no interchange dishes, user-added dishes become orphan nodes. Map, home recommendations, and capture matching each needed their own relation data.
- **Decision**: Dishes are defined by feature vectors (ingredients, seasonings, cooking method, step count, difficulty, genre). Relations are derived as undirected weighted-overlap scores (seasonings weighted high). Recommendations draw from a score band, not the maximum. Map = offline 2D projection of the score space with fixed shipped coordinates; user-added dishes placed at the score-weighted centroid of k nearest neighbors. Prerequisites: ingredient master normalization (76 raw strings → id + display name) and a dish-name alias table. Human review covers only the surfaced pairs of the bundled catalog (~600) plus intro texts, via the existing Notion review flow.
- **Rationale**: One structure solves five problems at once — bidirectionality, organic full connectivity, automatic graph membership for captured dishes, a single data source feeding home/search/map, and pantry-overlap weighting for "discover within my usual ingredients". Curation effort shifts from edge-writing (unscalable) to feature accuracy and bridge-dish placement (scalable). Full spec: spec-030 v2 (2026-07-04, owner GO).
