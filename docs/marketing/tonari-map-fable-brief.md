# となりごはん「マップ」創造ブリーフ — Fable向け

このドキュメントは、料理帳内の「マップ」ページのビジュアルコンセプトを**ゼロから創造的に考え直す**ための資料一式。正本はspec-030（体験設計）だが、マップの見た目そのものはまだ決着していない領域として扱ってよい。

## そもそも何のための機能か

となりごはんは「レシピを探すアプリ」ではなく「作れる料理を資産として育てる料理帳アプリ」。核となる価値は5層で言語化されている:

| 層 | 内容 |
|---|---|
| 機能 | 作った料理を記録し、それをもとに近い料理をおすすめする |
| 行動 | 「今日ちょっと別の料理にチャレンジしてみるか」と思う |
| 価値 | 料理レパートリーが無理なく増える |
| 感情 | 「探さなくても出てくる」「これなら作れそう」 |
| 記憶 | レシピを探すんじゃなくて、自分のレパートリーを育てるアプリ |

全機能はこの二本柱のどちらかに効かないと採用しない: **レパートリー拡大のコスト削減** と **モチベーション増加**。マップは完全にモチベ増加側の機能（冒険心・観賞・所有感）。ホームやおすすめのようなコスト削減の実務は担わない。

## マップに要求される4条件（観賞価値、オーナー言語化）

1. 自分の形をしている（自分のレパートリーが反映された、他人と同じにならない絵）
2. 時間が刻まれている（育ってきた過程が見える）
3. 見るたび発見がある
4. 絵として美しい

1と2はデータ構造が自動で満たす。**3と4がまさにビジュアルデザインの勝負** — ここがFableに考えてほしい部分。

## 位置づけ（確定・変更不可）

- 独立タブではなく、**料理帳タブ内の1ページ**（自分の一冊をめくると自分の地図がある、という配置）
- 3タブ構成: 探す / ホーム / 料理帳（マップは料理帳の中）
- 3層構造: **眺める層**（全体の絵。観賞・画像エクスポート・SNS共有）→ **つまむ層**（ノードタップ→下から写真+料理名+差分1行+所要時間のカード）→ **決める層**（詳しく見る→詳細画面）
- 撤退線あり: コンセプト画像でオーナーが「眺めたい・シェアしたい」と思えなければv1はマップなしで出す（成長サマリ1行で代替）。つまりここでの案が弱ければ不採用もありうる、というプレッシャーの中で考えてほしい

## データの土台（確定・変更不可 — ADR-009）

マップが描くのは「料理の宇宙」ではなく**ユーザー自身のレパートリーグラフ**。2026-07-04にデータ構造を転換した:

- 全料理は特徴量（食材・調味料・調理法・工程数・難易度・ジャンル）で定義され、**近さは無向のスコア**として自動計算される（手書きの関係リストではない）
- **地形は事前計算・固定出荷**: オフラインで一度だけ2次元投影し、人手で微調整して固定座標にする。ユーザーの利用中にレイアウトは動かない（「自分の地図」としての馴染みを壊さないため）
- 画面に描くのは全カタログ（150〜200皿）ではなく、**自分のレパートリー+スコア圏内のフロンティア**のみ。初日はオンボーディングで選んだ皿とその周辺だけが見え、作るたびに視界が広がる
- 探索の楽しみは2機構: ①点灯（調味料を「持ってる」登録すると解放される皿が光る）②海岸線バッジ（あと食材1つで作れる皿にマーク）
- ユーザーが追加した料理（外部キャプチャ経由）は、近傍k皿の固定座標の重み付き重心に配置される（再計算なしで意味的に正しい位置に決まる）

## 現在の暫定方針（2026-07-04時点。これも再検討対象にしてよい）

直近の壁打ちで「白地図の塗り絵」という方向を仮に置いた: 全皿が線画アウトラインで常に描かれ（名前も形もはっきり見える）、作った料理だけフルカラー+写真で塗られる。成長の可視化を「隠す→現す」ではなく「線画→彩色」でやる発想。**ただしこれはFableに考えさせる前の仮置きなので、これに縛られる必要はない**。データの土台（スコア投影・固定座標・フロンティア表示・点灯・海岸線バッジ）は変更不可だが、それをどう「絵」にするかは白紙で考えてほしい。

## 過去に不採用になった5案（実物と却下理由）

いずれも `tonari-app/mocks/concept/` 配下に画像あり。**同じ方向の焼き直しは避けたい**。

1. **路線図**（`gpt/map-metro.png`）: 料理を鉄道の駅に見立て、路線でつなぐ。却下理由: 線が「方向・進路の固定」を暗示し、「縦横無尽に広がる」というレパートリーの性質と矛盾する
2. **星座**（`gpt/map-constellation.png`）: 夜空に星座として配置。却下理由: 見た目は綺麗だが「眺めたいと思えない」（暗い夜空のトーンがアプリ全体の温かみと合わない、という感触も）
3. **庭**（`gpt2/map-garden.png`）: 料理が植物として生育段階（芽→株）で表現される。却下理由: 未検証だが、料理と植物の対応が恣意的（唐揚げがなぜ橙の花なのか等）で、覚えにくい・意味が読み取りにくい
4. **街**（`gpt2/map-town.png`）: 料理が店として並ぶ街並み。却下理由: 未検証だが、店舗の見た目のバリエーションが料理の特徴と結びついておらず、装飾止まりになるリスク
5. **放射グラフ/ネットワーク**（`gpt2/map-web.png`）: 料理を線でつなぐネットワーク図、食材アイコンが周辺に配置。却下理由: 星座案に近い抽象さ。「自分のレパートリーの形」が伝わりにくい

**5案に共通する反省**: 様式（鉄道・星座・庭・街・ネットワーク）から発想して、後からデータ（近さ・作った/作れる状態）を当てはめようとした。正しい順番は逆で、**データの形（自分の料理が中心、方向を持たない配置、近いものが近くにある）から先に決めて、そこに様式の皮をかぶせる**べきだった。

## Fableに考えてほしいこと（自由記述）

- 「近さスコアで配置された固定座標」「フロンティア（自分のレパートリー周辺だけ見える）」「点灯」「海岸線バッジ」というデータ的な制約を守った上で、**方向性を固定と読ませない、かつ観賞に耐える視覚様式**は何か
- 5案の失敗（進路固定を暗示/眺めたいと思えない/対応が恣意的/装飾止まり/抽象的すぎる）を踏まえ、「自分の形をしている」「見るたび発見がある」をどう絵として担保するか
- ズームの2段階（自分のレパートリー周辺⇄全体像）をどう視覚的に成立させるか
- 料理写真・イラストの様式は別トラックで検討中（round4、まだ確定していない）なので、マップの様式は料理イラストに依存しすぎない設計だと望ましい（写真なし版でも成立する強さがほしい）
- 全く新しい比喩を提案してもよい。5案（乗り物・天体・植物・建物・抽象図形）以外の領域から発想してもよい
